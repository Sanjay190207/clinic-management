PART 1: SYSTEM ARCHITECTURE & HIGH-LEVEL DESIGN OVERVIEW
================================================================================

The Clinic Appointment Management System follows a decoupled Client-Server architecture:
1. CLIENT (Frontend):
   - Single Page Application (SPA) built using React.js 18 and Vite.
   - Client-side routing managed by React Router DOM v7.
   - Global reactive state for authentication managed by React Context API.
   - HTTP communication handled by Axios with automatic request token attachment and 401 unauthenticated interceptors.
   - Custom responsive healthcare design system styled via pure CSS3 variables and utility classes.

2. SERVER (Backend):
   - RESTful API service built on Node.js and Express.js.
   - Stateless JWT (JSON Web Token) authentication with bearer authorization headers.
   - Password security via bcryptjs with salt factor 10.
   - Helmet security headers, CORS origin whitelisting, and IP-based rate limiting on authentication routes.
   - Centralized error handling catching Mongoose CastErrors, ValidationErrors, and MongoDB code 11000 duplicate keys.

3. DATABASE (Data Persistence):
   - MongoDB database operated via Mongoose ODM.
   - Atomic concurrency protection via compound unique partial indexes on appointments to strictly prevent double bookings.
   - Automatic cascade-awareness: soft-deactivation of departments with active doctors, release of appointment slots upon cancellation.

2.1 ROOT SERVER FILES
--------------------------------------------------------------------------------

1. [server/server.js]
   - Purpose: Main application entry point for the backend runtime.
   - Functions & Responsibilities:
     * Loads environment variables from root `.env` or local `.env` using dotenv.
     * Calls `connectDB()` to establish a connection to MongoDB before listening.
     * Starts the HTTP server on `PORT` (default: 5000).
     * Binds process-level listeners (`unhandledRejection`) to handle unexpected promises gracefully without crashing the server.
   - Connections:
     * Imports `connectDB` from `server/config/db.js`.
     * Imports configured Express application instance `app` from `server/app.js`.

2. [server/app.js]
   - Purpose: Express application assembly, middleware configuration, and route registration.
   - Functions & Responsibilities:
     * Attaches `helmet()` for secure HTTP response headers.
     * Configures `cors()` to permit incoming requests only from the authorized frontend origin (`CLIENT_URL`).
     * Parses incoming JSON and URL-encoded request bodies (`express.json({ limit: '1mb' })`).
     * Attaches `morgan('dev')` logging in development mode.
     * Mounts `authLimiter` (express-rate-limit) on `/api/auth` to prevent brute-force login attacks.
     * Defines system healthcheck endpoint: `GET /api/health`.
     * Mounts modular API route handlers under the `/api` prefix:
       - `/api/auth` -> `auth.routes.js`
       - `/api/departments` -> `department.routes.js`
       - `/api/doctors` -> `doctor.routes.js`
       - `/api/appointments` -> `appointment.routes.js`
       - `/api/patients` -> `patient.routes.js`
       - `/api/dashboard` -> `dashboard.routes.js`
       - `/api/users` -> `user.routes.js`
     * Catches undefined routes with a generic 404 JSON responder.
     * Mounts `errorHandler` centralized middleware at the very end of the pipeline.
   - Connections:
     * Imports all route files from `server/routes/`.
     * Imports `errorHandler` from `server/middleware/error.middleware.js`.
     * Exported to `server/server.js` and `server/scripts/run-tests.js`.

2.3 DATA MODELS & DATABASE SCHEMAS (models/)
--------------------------------------------------------------------------------

4. [server/models/User.js]
   - Purpose: Mongoose schema and model representing registered human users across all 4 system roles.
   - Fields:
     * `name` (String, required, trimmed, max 100)
     * `email` (String, required, unique, lowercase, trimmed, regex email validated)
     * `phone` (String, required, trimmed)
     * `password` (String, required, min 6, select: false to prevent accidental exposure)
     * `role` (Enum: `['patient', 'doctor', 'receptionist', 'admin']`, default: `'patient'`)
     * `isActive` (Boolean, default: true)
     * `timestamps` (createdAt, updatedAt)
   - Methods & Hooks:
     * `userSchema.pre('save')`: Hashes password using `bcrypt.hash()` with salt factor 10 if password was modified.
     * `userSchema.methods.matchPassword(enteredPassword)`: Compares candidate plaintext password against stored bcrypt hash using `bcrypt.compare()`.
   - Connections:
     * Used by `auth.controller.js` for registration/login.
     * Referenced by `Doctor.js` via `userId`.
     * Referenced by `Appointment.js` via `patientId` and `cancelledBy`.
     * Queried by `patient.controller.js` and `user.controller.js`.

5. [server/models/Department.js]
   - Purpose: Schema representing clinical medical specialties (e.g., Cardiology, General Medicine, Pediatrics).
   - Fields:
     * `name` (String, required, unique, trimmed, max 100)
     * `description` (String, required, trimmed, max 500)
     * `isActive` (Boolean, default: true)
     * `timestamps` (createdAt, updatedAt)
   - Connections:
     * Referenced by `Doctor.js` via `departmentId`.
     * Referenced by `Appointment.js` via `departmentId`.
     * Managed by `department.controller.js`.

6. [server/models/Doctor.js]
   - Purpose: Schema representing professional physician clinical profiles.
   - Fields:
     * `userId` (ObjectId referencing `User`, required, unique - enforces 1:1 relationship with a user account)
     * `departmentId` (ObjectId referencing `Department`, required)
     * `qualification` (String, required, e.g. "MBBS, MD (Cardiology)")
     * `experience` (Number, required, years of practice, min: 0)
     * `consultationFee` (Number, required, outpatient consultation rate in USD, min: 0)
     * `description` (String, required, doctor biography, max 1000)
     * `profileImage` (String, image URL)
     * `isActive` (Boolean, default: true)
     * `timestamps`
     * Virtual populate: `availability` referencing `DoctorAvailability` on foreignField `doctorId`.
   - Connections:
     * Links `User` and `Department`.
     * Referenced by `DoctorAvailability.js` and `Appointment.js`.
     * Managed by `doctor.controller.js`.

7. [server/models/DoctorAvailability.js]
   - Purpose: Schema defining weekly recurring shift schedules and protected break periods for each doctor.
   - Fields:
     * `doctorId` (ObjectId referencing `Doctor`, required)
     * `dayOfWeek` (Number, 0 = Sunday, 1 = Monday ... 6 = Saturday)
     * `dayName` (Enum string matching day name)
     * `startTime` (String, 24-hr `HH:mm`, e.g. "09:00")
     * `endTime` (String, 24-hr `HH:mm`, e.g. "17:00")
     * `slotDuration` (Number in minutes, default: 30, min: 10, max: 120)
     * `breakPeriods` (Array of subdocuments: `{ startTime, endTime, reason }` e.g. 13:00 - 14:00 Lunch Break)
     * `isAvailable` (Boolean, default: true)
   - Indexes:
     * `{ doctorId: 1, dayOfWeek: 1 }` (Unique compound index) - Guarantees that a physician has at most one schedule definition per day of the week.
   - Connections:
     * Read by `availability.controller.js` to dynamically generate open booking slots.

8. [server/models/Appointment.js]
   - Purpose: Schema representing booked, active, completed, or cancelled consultation visits.
   - Fields:
     * `appointmentReference` (String, unique, format `APT-YYYYMMDD-XXXX`)
     * `patientId` (ObjectId referencing `User`, required)
     * `doctorId` (ObjectId referencing `Doctor`, required)
     * `departmentId` (ObjectId referencing `Department`, required)
     * `appointmentDate` (String in `YYYY-MM-DD` ISO format, timezone safe)
     * `startTime` (String in `HH:mm` 24-hr format, e.g. "09:30")
     * `endTime` (String in `HH:mm` 24-hr format, e.g. "10:00")
     * `status` (Enum: `['Booked', 'Checked In', 'Completed', 'Cancelled', 'No Show']`, default: `'Booked'`)
     * `consultationFee` (Number, snapshot of fee at time of booking)
     * `reasonForVisit` (String, reason entered by patient)
     * `notes` (String, clinical notes added by physician or receptionist)
     * `cancelledAt` (Date, timestamp of cancellation)
     * `cancelledBy` (ObjectId referencing `User`)
     * `cancellationReason` (String)
     * `timestamps`
   - Indexes & Concurrency Protection:
     * Query indexes on `patientId`, `doctorId`, `departmentId`, `status`.
     * CRITICAL COMPOUND UNIQUE PARTIAL INDEX:
       `{ doctorId: 1, appointmentDate: 1, startTime: 1 }`
       `partialFilterExpression: { status: { $in: ['Booked', 'Checked In', 'Completed'] } }`
       Enforces atomic double-booking prevention in MongoDB storage engine. Automatically frees the slot when status transitions to `Cancelled` or `No Show`.
   - Connections:
     * Central model of the system; manipulated by `appointment.controller.js`.

2.4 SECURITY & ROUTING MIDDLEWARE (middleware/)
--------------------------------------------------------------------------------

9. [server/middleware/auth.middleware.js]
   - Purpose: Authenticates JSON Web Tokens and enforces Role-Based Access Control (RBAC).
   - Functions:
     * `protect(req, res, next)`: Extracts Bearer token from `req.headers.authorization`. Verifies token using `verifyToken()`. Queries `User.findById(decoded.id)`. Rejects if user does not exist or if `user.isActive === false`. Attaches sanitized user document to `req.user` and calls `next()`.
     * `authorize(...roles)`: Higher-order middleware accepting permitted roles (e.g. `authorize('admin')` or `authorize('admin', 'receptionist')`). Checks if `roles.includes(req.user.role)`. If matched, calls `next()`; otherwise returns `403 Forbidden`.
   - Connections:
     * Uses `verifyToken` from `server/utils/jwt.js`.
     * Used by all protected routes in `server/routes/`.

10. [server/middleware/error.middleware.js]
    - Purpose: Centralized Express error-handling middleware intercepting thrown exceptions.
    - Functions:
      * `errorHandler(err, req, res, next)`:
        - Logs error message with timestamp to server console.
        - Translates Mongoose `CastError` (invalid ObjectId) to `404 Resource not found`.
        - Translates Mongoose `ValidationError` to `400 Bad Request` with field-level error dictionary.
        - Translates MongoDB `code 11000` (Duplicate Key):
          * If duplicate key is on appointment `(doctorId, appointmentDate, startTime)`, returns `409 Conflict` with `conflict: 'SLOT_ALREADY_BOOKED'`.
          * If duplicate email, returns `409 An account with this email already exists`.
        - Translates `JsonWebTokenError` and `TokenExpiredError` to `401 Unauthorized`.
        - Returns safe JSON response without exposing internal server stack traces to clients.
    - Connections:
      * Mounted in `server/app.js` as the final middleware.

2.5 UTILITY MODULES (utils/)
--------------------------------------------------------------------------------

11. [server/utils/jwt.js]
    - Purpose: JWT generation and verification utility.
    - Functions:
      * `generateToken(id, role)`: Signs `{ id, role }` using `JWT_SECRET` with configurable expiry (default: `7d`).
      * `verifyToken(token)`: Decodes and verifies token signature and expiration.
    - Connections:
      * Used by `auth.controller.js` and `auth.middleware.js`.

12. [server/utils/timeUtils.js]
    - Purpose: Time calculations, slot division, break-time checks, and cutoff validation.
    - Functions:
      * `timeToMinutes(timeStr)`: Converts `"09:30"` to minutes from midnight (`570`).
      * `minutesToTime(totalMinutes)`: Converts `570` back to `"09:30"`.
      * `isOverlapping(start1, end1, start2, end2)`: Mathematical interval overlap check.
      * `isInBreakPeriod(slotStart, slotEnd, breakPeriods)`: Determines if a candidate slot overlaps with doctor lunch or rest periods.
      * `isPastDate(dateStr)`: Checks if a date string is strictly before today in clinic local time.
      * `isPastDateTime(dateStr, timeStr)`: Checks if a specific time slot on today's date has already elapsed.
      * `canCancelAppointment(appointmentDate, startTime, cutoffHours)`: Evaluates whether the appointment start time is at least `cutoffHours` (default: 2) in the future.
      * `generateSlots(availability, bookedSlots, dateStr)`: Iterates from shift start to shift end in steps of `slotDuration`. For each slot, marks `isAvailable: true` only if not in a break, not already booked, and not in the past.
    - Connections:
      * Core engine used by `availability.controller.js` and `appointment.controller.js`.

13. [server/utils/referenceGenerator.js]
    - Purpose: Generates human-readable, unique appointment reference identifiers.
    - Functions:
      * `generateAppointmentReference(dateStr)`: Combines prefix, date string, and cryptographically secure random hexadecimal characters (e.g. `APT-20261110-A9F3`).
    - Connections:
      * Used in `appointment.controller.js` and `scripts/seed.js`.

2.6 API ROUTE CONTROLLERS (controllers/)
--------------------------------------------------------------------------------

14. [server/controllers/auth.controller.js]
    - Purpose: Handles user authentication, registration, token issuance, and current session retrieval.
    - Handlers:
      * `register(req, res, next)`: Validates input; ensures email uniqueness; creates new `User` with role `'patient'`; returns JWT and user payload (status 201).
      * `login(req, res, next)`: Validates credentials; checks `isActive`; verifies password using `matchPassword()`; generates token; returns token and user payload (status 200).
      * `logout(req, res)`: Returns success confirmation for client-side token discard.
      * `getMe(req, res, next)`: Returns the current user profile from `req.user`.

15. [server/controllers/department.controller.js]
    - Purpose: CRUD operations on clinical medical departments.
    - Handlers:
      * `getDepartments`: Public endpoint listing active departments (or all if admin `?all=true`); aggregates active doctor count for each department.
      * `getDepartmentById`: Returns department info and list of active doctors assigned to it.
      * `createDepartment`: Admin-only endpoint creating new department with uniqueness check.
      * `updateDepartment`: Admin-only endpoint updating department details and active flag.
      * `deleteDepartment`: Admin-only endpoint; checks if active doctors exist—soft-deactivates if doctors exist, or hard-deletes if vacant.

16. [server/controllers/doctor.controller.js]
    - Purpose: Complete lifecycle management of doctors.
    - Handlers:
      * `getDoctors`: Public endpoint supporting search by doctor name/qualification and filtering by department.
      * `getDoctorById`: Retrieves doctor profile with populated User and Department, plus weekly availability schedule.
      * `createDoctor`: Admin-only atomic endpoint that creates both the `User` account (role: `'doctor'`) and `Doctor` profile, and provisions default Monday–Friday availability schedules.
      * `updateDoctor`: Admin or the doctor themself updating qualifications, experience, description, and fee.
      * `toggleDoctorStatus`: Admin endpoint activating or deactivating doctor and their underlying user account.
      * `deleteDoctor`: Admin endpoint soft-deactivating doctor account to preserve historical appointment references.

17. [server/controllers/availability.controller.js]
    - Purpose: Doctor shift schedule configuration and real-time slot generation.
    - Handlers:
      * `getDoctorAvailability`: Returns configured weekly schedules for a given doctor.
      * `getAvailableSlots`: Core public slot calculation endpoint. Given `date=YYYY-MM-DD`, determines day of week, looks up schedule, fetches active appointments (`Booked`, `Checked In`, `Completed`), and invokes `generateSlots()` to return available slot array.
      * `setDoctorAvailability`: Upserts working schedule and break periods for a doctor on a specific day of the week.
      * `updateDoctorAvailability`: Updates specific availability record by ID.

18. [server/controllers/appointment.controller.js]
    - Purpose: Core appointment booking, retrieval, status transition, and cancellation engine.
    - Handlers:
      * `bookAppointment`:
        - Validates input format (YYYY-MM-DD and HH:mm).
        - Verifies doctor exists and `isActive === true`.
        - Verifies date/time is not in the past.
        - Verifies slot falls within doctor's working schedule and does not overlap with break periods.
        - Pre-checks active appointments.
        - Generates reference code and executes `Appointment.create()`.
        - Catches MongoDB duplicate key error code 11000 and responds with `409 Conflict` if a concurrent user booked the slot simultaneously.
      * `getMyAppointments`: Returns appointments for the authenticated user. If `role === 'patient'`, filters by `patientId`; if `role === 'doctor'`, filters by `doctorId`. Supports `?upcoming=true`.
      * `getAppointmentById`: Returns single appointment with security checks (patient owner, assigned doctor, or clinic staff).
      * `cancelAppointment`: Cancels an appointment if in `Booked` status. Enforces `canCancelAppointment()` cutoff threshold for patients. Releases the slot for re-booking.
      * `updateAppointmentStatus`: Transitions appointment status (`Checked In`, `Completed`, `No Show`). Enforces that doctors can ONLY update their own appointments and follow valid status transitions.
      * `getAllAppointments`: Master list for Admin and Receptionist with date, status, doctor, and patient search filters and pagination.

19. [server/controllers/patient.controller.js]
    - Purpose: Registered patient management and privacy enforcement.
    - Handlers:
      * `getPatients`: Admin and Receptionist endpoint listing registered patients with their booking count and search filters.
      * `getPatientById`: Retrieves patient profile and appointment history. Enforces strict privacy (patients can only view themselves; doctors can only view patients with whom they have an appointment).
      * `updatePatientProfile`: Allows patient to update permitted fields (`name`, `phone`).

20. [server/controllers/dashboard.controller.js]
    - Purpose: High-performance aggregated analytics for dashboards.
    - Handlers:
      * `getPatientDashboard`: Calculates total bookings, upcoming visits, completed visits, cancelled visits, next appointment spotlight card, and recent 5 bookings for the patient.
      * `getDoctorDashboard`: Calculates today's patient queue, pending consults, completed consults, total bookings, upcoming visits, and weekly schedule for the doctor.
      * `getAdminDashboard`: Aggregates clinic-wide statistics: total patients, total active doctors, total departments, total appointments, today's appointments, upcoming, completed, cancelled, and recent clinic activity.

21. [server/controllers/user.controller.js]
    - Purpose: Privileged user account management (Admin only).
    - Handlers:
      * `getUsers`: Lists system users filtered by role.
      * `createUser`: Creates staff accounts (receptionist or admin).
      * `toggleUserStatus`: Activates or deactivates user accounts (guards against admin deactivating their own account).

PART 5: COMPLETE END-TO-END SYSTEM WORKFLOWS (FLOW EXPLANATIONS)
================================================================================

--------------------------------------------------------------------------------
5.1 FLOW 1: USER REGISTRATION & AUTHENTICATION FLOW
--------------------------------------------------------------------------------

1. User visits `/register` and enters Name, Email, Phone, and Password.
2. `Register.jsx` validates input on the client and calls `register()` from `AuthContext.jsx`.
3. `AuthContext.jsx` issues `POST /api/auth/register` to Express backend via Axios.
4. `auth.routes.js` routes request to `register()` in `auth.controller.js`.
5. Controller verifies email uniqueness in `User` collection.
6. `User.js` pre-save hook hashes password using bcrypt with salt factor 10.
7. Record is saved in MongoDB; `generateToken()` creates signed JWT with user ID and role (`'patient'`).
8. Backend returns 201 Created with token and user object.
9. `AuthContext.jsx` saves token and user to `localStorage` and updates application state.
10. User is immediately redirected to `/patient/dashboard`.

Subsequent Logins:
- User submits credentials on `/login`.
- `auth.controller.js` finds user, selects hidden `password`, and calls `user.matchPassword()`.
- If valid and `isActive: true`, issues fresh JWT.
- Client stores token; Axios interceptor attaches it to all future requests.


--------------------------------------------------------------------------------
5.2 FLOW 2: DOCTOR CREATION & WORKING HOURS PROVISIONING FLOW
--------------------------------------------------------------------------------

1. Administrator logs in and navigates to `/admin/doctors/new`.
2. Admin fills doctor details (Credentials, Department, Qualifications, Experience, Consultation Fee, Bio).
3. `AddDoctor.jsx` submits `POST /api/doctors` with Bearer token.
4. `auth.middleware.js` verifies token and verifies `req.user.role === 'admin'`.
5. `doctor.controller.js` executes:
   a. Creates `User` account with `role: 'doctor'`.
   b. Creates `Doctor` record linking `userId` and `departmentId`.
   c. Automatically provisions default availability schedules in `DoctorAvailability` collection for Monday through Friday (09:00 - 17:00, 30 min slots, 13:00 - 14:00 lunch break).
6. Administrator or Doctor can navigate to `/doctor/weekly` or `/admin/working-hours` to customize specific shift hours and break periods via `POST /api/doctors/:id/availability`.


--------------------------------------------------------------------------------
5.3 FLOW 3: SLOT GENERATION & ATOMIC APPOINTMENT BOOKING FLOW
--------------------------------------------------------------------------------

Slot Generation:
1. Patient visits `/patient/book/:doctorId` and selects an appointment date.
2. `BookAppointment.jsx` triggers `GET /api/doctors/:doctorId/slots?date=YYYY-MM-DD`.
3. `availability.controller.js` handles request:
   a. Checks if date is strictly in the past (rejects if past).
   b. Determines day of week (e.g., 2026-11-23 is Monday = 1).
   c. Fetches doctor's schedule from `DoctorAvailability`.
   d. Queries `Appointment` collection for active bookings on that date (`status: { $in: ['Booked', 'Checked In', 'Completed'] }`).
   e. Calls `timeUtils.generateSlots()`:
      - Iterates from shift start to end in steps of `slotDuration`.
      - Checks each slot against lunch break periods (`isInBreakPeriod`).
      - Checks if slot is already booked.
      - Checks if slot is in the past for today's date.
      - Returns array of slots marked `isAvailable: true/false` with status reason.
4. `BookAppointment.jsx` renders slots as green (open) or grey (break/booked) buttons.

Booking & Race Condition Prevention:
5. Patient clicks an open slot (e.g. 10:00 AM) and clicks "Confirm Appointment".
6. Client sends `POST /api/appointments` with `doctorId`, `appointmentDate`, `startTime`.
7. `appointment.controller.js`:
   a. Re-validates doctor active status, date, shift bounds, and break overlap.
   b. Generates unique reference code (e.g. `APT-20261123-B8C1`).
   c. Executes `Appointment.create()`.
   d. SCENARIO A (Standard): Write succeeds. Returns 201 Created with populated appointment. Client redirects to `/patient/confirmation/:id`.
   e. SCENARIO B (Simultaneous Double Booking Race Condition):
      - Another patient confirmed the exact same slot at the exact same millisecond.
      - MongoDB's compound unique partial index `{ doctorId: 1, appointmentDate: 1, startTime: 1 }` rejects the second write with error code `11000`.
      - `appointment.controller.js` catches code 11000 and responds with `HTTP 409 Conflict` and `conflict: 'SLOT_ALREADY_BOOKED'`.
      - `BookAppointment.jsx` catches 409, alerts the patient, and automatically re-fetches open slots so the patient can choose another slot.


--------------------------------------------------------------------------------
5.4 FLOW 4: CLINIC CONSULTATION FLOW (DOCTOR WORKFLOW)
--------------------------------------------------------------------------------

1. On the appointment day, the patient arrives at the clinic.
2. Doctor (or Receptionist) views `/doctor/today` or `/admin/appointments`.
3. Doctor clicks "Check In" button:
   - Client sends `PATCH /api/appointments/:id/status` with `status: 'Checked In'`.
   - Backend updates status to `Checked In`. Badge updates to yellow on all screens.
4. Doctor conducts consultation with patient.
5. Doctor clicks "Complete":
   - Modal prompts doctor for consultation notes, diagnosis, and prescription advice.
   - Doctor enters notes and confirms.
   - Client sends `PATCH /api/appointments/:id/status` with `status: 'Completed'` and `notes: '...'`.
   - Backend saves notes and transitions status to `Completed`.
6. Patient can now view these notes anytime under `/patient/history`.


--------------------------------------------------------------------------------
5.5 FLOW 5: APPOINTMENT CANCELLATION & SLOT RELEASE FLOW
--------------------------------------------------------------------------------

1. Patient views their scheduled appointment under `/patient/appointments` and clicks "Cancel".
2. Modal opens displaying the clinic cancellation policy (minimum 2 hours in advance).
3. Patient provides cancellation reason and confirms.
4. Client sends `PATCH /api/appointments/:id/cancel`.
5. `appointment.controller.js`:
   a. Verifies user ownership (`appointment.patientId === req.user._id`).
   b. Calls `canCancelAppointment(appointmentDate, startTime, cutoffHours)`:
      - If remaining time < cutoff (e.g., 1 hour before visit), returns `400 Bad Request` with hours remaining.
   c. If valid, updates appointment:
      - `status = 'Cancelled'`
      - `cancelledAt = new Date()`
      - `cancelledBy = req.user._id`
      - `cancellationReason = '...'`
   d. Saves appointment.
6. SLOT RELEASE MECHANISM:
   - Because the database compound unique index only indexes `{ status: { $in: ['Booked', 'Checked In', 'Completed'] } }`, transitioning to `'Cancelled'` automatically removes the appointment from the index constraint.
   - The slot is instantly free and appears as available in subsequent slot lookups for any patient.


--------------------------------------------------------------------------------
5.6 FLOW 6: ROLE-BASED AUTHORIZATION & PROTECTED ROUTE FLOW
--------------------------------------------------------------------------------

1. Incoming Request on Client:
   - User navigates to a URL (e.g. `/admin/users`).
   - `App.jsx` evaluates `<ProtectedRoute allowedRoles={['admin']}>`.
   - `ProtectedRoute.jsx` checks `useAuth()`:
     * If unauthenticated: redirects to `/login`.
     * If user role is `patient`: redirects to `/patient/dashboard`.
     * If user role is `doctor`: redirects to `/doctor/dashboard`.
     * If user role is `admin`: renders component.
2. Backend API Verification:
   - Client makes HTTP request to `/api/users`.
   - Express router evaluates: `router.use(protect, authorize('admin'))`.
   - `protect` verifies JWT and loads `req.user`.
   - `authorize('admin')` checks `req.user.role === 'admin'`.
     * If a receptionist or patient token is sent, backend responds with `403 Forbidden`.
   - Ensures end-to-end security enforced at the server layer regardless of client manipulation.
